# BEMO — أساس الحسابات والمتاجر الجاهز للاعتماد

**تحديث:** اعتمد المالك هذه المراجعة وطُبّق الأساس. هذا سجل العرض قبل الاعتماد؛ الحالة الحالية ونتائج الفحص في `FOUNDATION_DELIVERY_AR.md`.

التاريخ: ٣ نوفمبر ٢٠٢٦. الحالة: اختُبر محلياً؛ لم يطبّق على Supabase ولم يربط بالواجهة.

## ما أُنجز فعلاً
- أُنشئ مشروع **BEMO Development** داخل المؤسسة التي اختارها المالك، بعد تأكيد تكلفة معروضة **0 دولار شهرياً**. المعرّف: `qjtsfdfcczxowsfjtrwy`، المنطقة: فرانكفورت `eu-central-1`، الحالة عند الإنشاء: `ACTIVE_HEALTHY`.
- فحص القاعدة الجديدة أثبت أن `public` فارغ، ولم يُرجع فحص الأمن تنبيهات. لم يتغير المشروع القديم المتوقف.
- أُعد أساس SQL قابل للمراجعة: حسابات التطبيق، أدوار إدارية داخلية غير ممنوحة لأي مستخدم، المتاجر، أسماء الروابط المحجوزة، وسجل الأحداث. هذه خمسة جداول داخلية.
- ست عمليات محددة: إنشاء/تحميل الملف الشخصي، قراءته، تعديل الاسم واللغة، إنشاء متجر واحد فوراً، قراءة متجر المالك، ودليل عام للمتاجر دون بريد المالك أو معرّفه.
- يتحقق الخادم من هوية Google وبريد Gmail المؤكد والجلسة، ويرفض الحسابات الموقوفة والجلسات المحذوفة. لا يعتمد على بيانات صلاحيات يرسلها المستخدم.
- قيود قاعدة البيانات تمنع المتجر الثاني وتكرار رابط المتجر أو اسمه. تكرار الطلب نفسه يعيد النتيجة الأصلية دون إنشاء متجر آخر.
- **31 اختباراً نجحت** على PostgreSQL محلي عبر PGlite، تشمل السماح والرفض، عزل الحسابات، منع منح الصلاحيات ذاتياً، الخصوصية، التعليق، التكرار، والأثر الكامل للمعاملة. راجع وكيل مستقل المسودة ولم يجد مشكلة مانعة ضمن نطاقها.

## ما سيحدث عند الاعتماد
تطبيق هذا الأساس الإضافي على مشروع التطوير الجديد فقط، ثم فحص صلاحياته وواجهاته على Supabase. الواجهة المعتمدة ستظل مستخدمة؛ لا إعادة بناء. لا رسوم منصة أو محافظ أو OTP أو توثيق إلزامي. لا تُحوّل بيانات العرض إلى عملاء أو طلبات أعمال.

هذا اعتماد **لأساس الحسابات والمتجر الواحد فقط**، وليس اعتماداً لبقية أنظمة المخزون والدفع والشارات أو للإطلاق العام.

## إعادة الاستخدام والاعتمادات
استخدمنا اختيار PostgreSQL/Supabase الموجود في المخطط، وحافظنا على ملفات الواجهة والتصميم والكتالوج التجريبي. لا إطار واجهة جديد ولا خدمة مدفوعة. `@electric-sql/pglite` نسخة `0.5.14` اعتماد اختبار محلي فقط، مرخص Apache-2.0 مع مكونات PostgreSQL المرخصة ضمن الحزمة؛ لا يُشحن في الموقع. الحزمة بلا اعتمادات تشغيل إضافية وفق سجلها، وبحجم مفكوك يقارب 26.4 MB. ثُبتت النسخة بملف قفل وسلامة SHA-512 ومن دون تشغيل install scripts. فحص npm audit بتاريخ التقرير أعاد صفر ثغرات مسجلة؛ لا يمثل ذلك ضماناً أمنياً شاملاً. [مرجع PGlite الرسمي](https://pglite.dev/docs/about).

## الملفات
- `backend/foundation-draft/foundation.sql`: المسودة كاملة، لم تُطبّق.
- `backend/foundation-draft/foundation.test.mjs`: الاختبارات القابلة لإعادة التشغيل.
- `backend/foundation-draft/contract.md`: العمليات والصلاحيات والقيود.
- `backend/foundation-draft/package.json` و`package-lock.json`: اعتماد الاختبار المثبت.
- `docs/GOOGLE_SETUP_AR.md`: خطوات إعداد Google للمشروع الجديد.
- `RESUME_BEMO.md` في مجلد العمل الرئيسي: نقطة الاستئناف والموافقات والمهام المتبقية.

## ما لم يُختبر أو يُنجز بعد
- تسجيل Google الحقيقي، إعداد المزود وصفحة العودة، وتجديد الرموز على الموقع.
- عزل البيانات عبر API المنشور والتزامن بين اتصالات فعلية. اختبارات PGlite تستخدم جداول هوية وحسابات اصطناعية محلية؛ ليست اختبار OAuth أو توقيع JWT.
- PGlite يعمل هنا على PostgreSQL 18.6؛ يلزم اختبار مسودة SQL على نسخة مشروع Supabase الفعلية قبل تشغيلها للمستخدمين.
- إدارة الأدوار الإدارية، العناوين والتوصيل والفئات، المنتجات والمخزون والطلبات الفعلية والشارات والمراجعات والحذف بعد 30 يوماً.
- القاعدة تستخدم فحص الجلسة ووقت انتهائها إن وجد؛ لا تدّعي سياسة انتهاء بالخمول. يلزم ضبط Google كمزود وحيد لأن قيمة OAuth في الرمز لا تسمّي مزوداً محدداً.

## بوابة الاعتماد
طلب المالك الأصلي يلزم بعرض أثر التعديلات المعمارية الكبيرة واعتمادها قبل التنفيذ. إضافة أساس البيانات المشترك خطوة معمارية جديدة مقارنة بالعرض الحالي المحفوظ في المتصفح. لذلك المسودة والاختبارات جاهزة، والتطبيق السحابي ينتظر اعتماد هذه الخطوة المحددة. إنشاء المشروع المجاني نفسه أُنجز بموافقة مستقلة سابقة.

تقدير المشروع الكلي السابق 35% ليس قياساً آلياً؛ لا نرفعه لمجرد إنشاء مشروع فارغ أو نجاح اختبارات محلية. تقرير هذه المرحلة يثبت الأعمال المحددة أعلاه فقط.
