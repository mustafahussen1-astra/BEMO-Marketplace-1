# BEMO — قائمة ربط الخدمات ومتطلبات الإطلاق

**تاريخ المراجعة:** ٢ نوفمبر ٢٠٢٦. **الحالة:** دليل إعداد؛ لم يُنشأ حساب أو مشروع، ولم يُطبّق SQL أو يُربط OAuth بهذه المراجعة.

اعتماد التصميم لا يثبت جاهزية الخلفية. المشروع المفحوص ما زال يعتمد على كتالوج ونشاط تجريبي في المتصفح؛ ملف `BACKEND_EXTENSION_PLAN_AR.md` خطة، وليس قاعدة بيانات منفّذة. أكّد المالك أنه لا يملك مشروع Supabase بعد.

## القائمة العملية بالترتيب

1. **ثبّت ملكية الخدمات ونطاق مرحلة الربط.** يستخدم BEMO حساب Supabase ومشروع Google Cloud يملكهما المالك. قبل تشغيل خلفية جديدة، يعتمد المالك أثرها المعماري وبيئة الاختبار ومنطقة استضافة البيانات والخطة المناسبة لميزانيته. لا يلزم شراء خدمة بحث أو بوابة دفع لهذه المرحلة، ولا يتم اختيار اشتراك مدفوع تلقائياً.

2. **أنشئ مشروع Supabase في حسابك.** احتفظ بكلمة مرور قاعدة البيانات داخل مدير كلمات المرور. بعد جاهزية المشروع، انسخ **Project URL** ومفتاح **Publishable** الذي يبدأ عادة بـ`sb_publishable_` من نافذة Connect أو إعدادات API Keys. هذان هما المدخلان العامّان المطلوبان لربط عميل الموقع. المفتاح العام ليس صلاحية إدارة؛ حماية السجلات تعتمد على تسجيل المستخدم وسياسات قاعدة البيانات. [توثيق مفاتيح Supabase](https://supabase.com/docs/guides/getting-started/api-keys).

3. **جهّز Google OAuth في مشروع تملكه.** من Google Auth Platform حدّد بيانات التطبيق وبريد الدعم والجمهور المناسب لحسابات Gmail الخارجية، واستخدم صلاحيات الهوية الأساسية فقط: `openid` والبريد والملف الشخصي. أنشئ OAuth Client من نوع **Web application**. أضف أصل الموقع الحالي إلى Authorized JavaScript origins:

   `https://bemo-marketplace-studio.supplecinch1.chatgpt.site`

   انسخ **Callback URL** من صفحة Google provider داخل مشروع Supabase، والصقه حرفياً في Authorized redirect URIs لدى Google. أضف Client ID وClient Secret داخل صفحة Google provider في Supabase وفعّل المزود. **السر يبقى هناك ولا يُرسل في الدردشة.** [دليل Google مع Supabase](https://supabase.com/docs/guides/auth/social-sign-in/auth-google).

4. **اضبط عودة المستخدم إلى BEMO.** في Supabase → Authentication → URL Configuration اضبط Site URL على أصل الموقع أعلاه. يحدد فريق التنفيذ مسار العودة الفعلي عند كتابة تدفق تسجيل الدخول؛ أضف ذلك الرابط الدقيق إلى Redirect URLs، دون wildcard واسع في الإنتاج. **هذا مختلف عن Callback URL الذي أُضيف إلى Google في الخطوة السابقة.** لا تضف مساراً غير منفّذ تخميناً. [إعداد روابط العودة](https://supabase.com/docs/guides/auth/redirect-urls).

5. **أرسل بيانات الربط العامة فقط عند الجاهزية.** المطلوب في الدردشة: Project URL، Publishable key، وتأكيد تفعيل Google وضبط روابط العودة. لا ترسل Client Secret أو `sb_secret_` أو `service_role` أو كلمة مرور قاعدة البيانات أو رموز الجلسات. إذا احتاجت مهمة خادم لاحقاً صلاحية مرتفعة، تُضبط عبر وسيلة أسرار مخصصة وبصلاحية محدودة، ولا توضع في JavaScript المتصفح أو المستودع. [حدود المفاتيح العامة والسرية](https://supabase.com/docs/guides/getting-started/api-keys).

6. **نفّذ قاعدة البيانات والصلاحيات في بيئة الاختبار بعد الاعتماد.** تُراجع الترحيلات قبل تطبيقها، ثم تُختبر الحسابات والمتجر الواحد والمنتجات والتوصيل والطلبات والمخزون والعزل. لا توجد ترحيلات مكتملة يُطلب تشغيلها الآن. بعد أول تسجيل ناجح يُحدد حساب المالك بمعرّف مستخدم موثوق ويُعيّن دور الإدارة من قناة إدارية محمية؛ لا يمكن للمستخدم اختيار دور admin في نموذج أو بيانات ملفه الشخصي.

7. **اختبر بهويات مستقلة قبل دعوة المشترين.** نحتاج حساب مالك، وبائعين مستقلين، ومشتري، وحساب دعم عند تنفيذ دوره. يتولى أصحاب الحسابات تسجيل الدخول بأنفسهم. تشمل الأدلة: نجاح Google/Gmail، رفض مزود أو بريد غير مسموح، انتهاء الجلسة، منع متجر ثانٍ، منع قراءة طلب متجر آخر، وعدم كشف العنوان قبل القبول. إعداد المزود وحده لا يثبت هذه الضمانات.

8. **جهّز الإطلاق العام بعد نجاح الاختبارات.** اسم التطبيق وبريد الدعم وصفحات الخصوصية والشروط وبيانات الجهة المشغّلة يجب أن تكون حقيقية. قد تتطلب علامة OAuth مراجعة Google وإثبات ملكية النطاقات؛ نراجع النطاق المستضاف الحالي وإمكان إثبات ملكيته قبل افتراض صلاحيته لعلامة إنتاجية. لا نشتري نطاقاً أو نغيّر الاستضافة تلقائياً. يبقى اختبار OAuth منفصلاً عن وعد ظهور علامة موثقة أو موعد قبول مراجعتها. [متطلبات Google للتحقق من العلامة](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification).

## ما يمكن إكماله دون هذه الحسابات

- دمج التصميم المعتمد واختبار الجوال وRTL/LTR والوصول بلوحة المفاتيح.
- تدفقات البائع والمشتري والدعم من ناحية الواجهة، مع وسم أي بيانات اختبار بوضوح.
- عقود API ومخطط البيانات ومراجعة الصلاحيات وخطة الترحيل والرجوع؛ وبعد اعتماد المرحلة المعمارية يمكن كتابة الشيفرة واختبارها محلياً.
- منطق الفلاتر وواجهات موفر البحث، واختبارات الوحدات بحالات منظمة معلنة.
- إعداد قائمة اختبارات أمان ومعاملات ومهام مجدولة وخطة نسخ واستعادة.

**ما لا يمكن إثباته بعد:** تسجيل Google الحقيقي، تطبيق RLS على مشروع المالك، حفظ الطلبات بين الأجهزة، سلامة التزامن تحت بيئة الاستضافة، المهام المجدولة الفعلية، خصوصية أدلة التوثيق، واستعادة نسخة احتياطية تشغيلية. لا تُوصف هذه الأجزاء بأنها مكتملة لمجرد وجود شاشة أو خطة.

## القرارات غير المحسومة فعلاً

هذه قرارات لاحقة للإطلاق أو للميزة المعنية، وليست كلها شرطاً لبدء بناء الواجهة:

| القرار الناقص | المرحلة التي يحتاجها | ما يمكن مواصلته قبله |
|---|---|---|
| العملة/العملات وقواعد الضرائب والاستيراد والعرض عند اختلاف العملات | تسعير وطلب حقيقي | عرض USD التجريبي دون افتراض أنه قرار عالمي |
| نوافذ الإرجاع حسب الفئة، المسؤولية عن شحن الإرجاع، السياسات القانونية وبيانات الجهة المشغّلة | قبول مشتريات تجارية | بناء مسار الحالة دون اختراع أهلية قانونية |
| مدة الاحتفاظ بأدلة الهوية/البلاغات وبيانات مكافحة إساءة التسجيل والاستثناءات القانونية | جمع بيانات حساسة وإطلاق الحذف الفعلي | تصميم تخزين خاص وسياسات وصول |
| معايير مستندات الأزرق والذهبي، المخوّلون بالمراجعة ونطاق التفويض والانتهاء | منح شارات حقيقية | الطلب والاعتراض والمعاينة بلا منح |
| الحدود العددية للأخضر وتعريف العينات والمؤشرات المؤهلة | منح تلقائي للأخضر | حساب تجريبي ومعاينة دون تفعيل |
| أسماء مسؤولي الدعم والإدارة والتصعيد، مسؤول النسخ والمراقبة | التشغيل مع مستخدمين حقيقيين | تنفيذ الأدوار دون منحها اعتباطياً |
| أهداف فقد البيانات ومدة الاستعادة، احتفاظ النسخ وتواتر تصديرها وميزانيتها | التجربة التشغيلية والإطلاق | إعداد خطة الاستعادة واختبارها عند توافر البيئة |
| نشر الموقع للعامة أو تحديد جمهور التجربة | وصول المشترين خارج حساب المالك | تطوير واختبار الموقع الخاص |

**قرارات محسومة لا نعيد سؤال المالك عنها:** Google مع Gmail وفق §05؛ متجر واحد وفوري بلا KYC إلزامي؛ التذكير ٢٤ ساعة والتصعيد ٤٨ ساعة دون إلغاء آلي؛ طلب حذف الحساب بعد ٣٠ يوماً مع استثناءات الاحتفاظ؛ COD للبائع؛ صفر رسوم منصة؛ لا محافظ أو عمولات أو OTP أو دردشة في V1. ولا نطلب اختيار بلد إجباري لأن المخطط يرفض قفل BEMO جغرافياً؛ تحدد تغطية كل بائع أهلية التوصيل.

## نقاط يجب عدم الخلط بينها

- **بوابة ChatGPT الخاصة مقابل Google:** الموقع المنشور خاص ويطلب ChatGPT للوصول. إبقاء ذلك أثناء الاختبار ممكن، لكنه لا يحقق تجربة تصفح عام وتسجيل Google فقط. تعديل الجمهور قرار نشر مستقل، وليس جزءاً تلقائياً من ربط Supabase.
- **KYC اختياري مقابل إنشاء متجر فوري:** مستندات الأزرق والذهبي شرط للشارة المعنية، لا شرط لفتح متجر.
- **اعتماد الشكل مقابل الخلفية:** طلب مواصلة المشروع يسمح بالأعمال الموافقة للمرحلة، لكن التوجيه الأخير يشترط عرض أثر التغيير المعماري واعتماده. لا يُستنتج اعتماد قاعدة إنتاجية من الموافقة على لقطات التصميم.
- **التقدير الزمني:** لا يوجد تاريخ إطلاق موثوق قبل تثبيت نطاق المرحلة وتوافر الحسابات ونتائج الاختبارات. مدة إعداد الحساب أو مراجعة Google خارج وقت تنفيذ الواجهة، ولا تُضمّن بوعد ثابت.

**نتيجة هذه المراجعة:** أُعدت هذه القائمة اعتماداً على ملفات المشروع والمخطط والمراجع الرسمية أعلاه. لم تُنشأ خدمات أو مفاتيح، ولم تُعدّل إعدادات استضافة أو حسابات أو قاعدة بيانات.
