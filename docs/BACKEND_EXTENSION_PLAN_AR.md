# BEMO — خطة امتدادات الخلفية للشارات والبحث

**التاريخ:** ١ نوفمبر ٢٠٢٦  
**الحالة:** خطة للمراجعة والاعتماد؛ لا SQL تنفيذي، ولا ترحيل بيانات، ولا ربط خدمة جديد ضمن هذا الملف.

## ١. ما أثبته فحص المشروع

راجعت الملفات الموجودة فعلياً: `dist/index.html` و`dist/styles.css` و`dist/catalog.js` و`dist/app.js`، إضافة إلى نموذج البحث المنفصل `dist/design-preview/search.html` و`search.js` و`search-fixtures.js` وملف `docs/PROTOTYPE_PLAN_AR.md`.

- المتجر الحالي HTML/CSS/JavaScript ثابت. البحث يرشّح مصفوفة الكتالوج داخل المتصفح.
- المنتجات والمتاجر افتراضية. السلة والمفضلات والطلبات التجريبية تُحفظ في `localStorage`، وليست سجلات أعمال مشتركة بين الأجهزة.
- لا يوجد مخطط قاعدة بيانات منفّذ أو API خاص بالمتجر أو نظام شارات حقيقي في الملفات المفحوصة. لا يوجد مشروع Supabase لدى المالك حتى الآن.
- تسجيل Google/Supabase المذكور في المخطط غير متصل. بوابة ChatGPT التي تحمي الموقع الخاص هي حماية استضافة منفصلة، وليست إثباتاً لتنفيذ هوية BEMO.
- نموذج البحث الجديد يستخدم `BemoSearchProvider` ووجهات وشارات ومخزوناً اصطناعياً معلناً. يصلح لإثبات سلوك الواجهة والفلاتر فقط؛ لا يجوز تحويل بياناته إلى منح توثيق أو عروض تجارية حقيقية.
- لم تُكتب أو تُطبّق ترحيلات خلفية في هذه المرحلة. لا توجد قاعدة إنتاجية تغيّرت بهذا العمل.

لذلك ستكون الإضافة الخلفية **إنشاء أساس تشغيل غير موجود حالياً** مع الحفاظ على الواجهة الحالية، لا استبدال قاعدة بيانات عاملة. يتطلب هذا الأثر المعماري اعتماد المالك قبل التنفيذ.

## ٢. المرجعية وما يجب الحفاظ عليه

المراجع المقروءة: المخطط الرئيسي V4.2، الملخص 02 الخاص بالشارات، الملخص 03 الخاص بالبحث، وتوجيه التطوير التدريجي الأخير. لا تُستخدم العبارات الإجرائية داخل الملفات لتجاوز موافقة المالك المطلوبة في التوجيه الأخير.

تبقى القواعد التالية دون تغيير:

1. متجر واحد لكل حساب، وإنشاء المتجر فور تسجيل الدخول دون KYC إلزامي أو موافقة إدارية مسبقة.
2. Google عبر Supabase هو مسار الهوية المطلوب. شرط Google وحساب Gmail يُتحقق منه في الخادم عند تنفيذ الهوية، لا بفحص نصي في المتصفح وحده.
3. سلة متعددة المتاجر، وطلب فرعي مستقل لكل بائع. لا يُخصم المخزون إلا عند قبول البائع، ولا تظهر له بيانات تسليم المشتري التفصيلية قبل نجاح القبول.
4. التوصيل ورسومه يحددهما البائع، وCOD يُدفع للبائع أو مندوبه. رسوم المنصة تظل صفراً، ولا محافظ أو تحصيل إلكتروني أو تفعيل وحدات مخفية.
5. التوثيق اختياري ومنفصل عن إنشاء المتجر. وجود Google أو سجل متجر لا يثبت هوية تجارية، وحالة COD المبلّغ عنها لا تثبت تحصيل أموال أو تفويض علامة.

## ٣. خطة الدمج التدريجي وإعادة الاستخدام

| المرحلة المقترحة | العمل | ما يعاد استخدامه | بوابة الخروج |
|---|---|---|---|
| المراجعة والتصميم الحاليان | نموذج رئيسية وبحث مستقل، تقرير فجوات، عقود منطقية | HTML/CSS/JS والكتالوج والصور التوضيحية وRTL | اعتماد الشكل والأثر المعماري |
| أساس البيانات والهوية | Supabase، مخطط متجر/منتج/توصيل، سياسات صلاحيات، Google | معرفات مستقرة وواجهات العرض الحالية بعد مواءمة البيانات | حسابات اختبار متعددة، رفض الوصول غير المصرح به، OAuth فعلي |
| شارات يدوية أولاً | الطلبات والأدلة والمراجعة والمنح والإلغاء والتاريخ | عنصر الشارة المرئي المعتمد؛ بلا إعادة بناء المتجر | معايير أدلة معتمدة واختبارات صلاحيات وتسريب |
| البحث عبر PostgreSQL | موفر بيانات خلفي بديل، فهارس وفلترة وشحن منظم | حدود `SearchProvider` وشكل URL والفلاتر | اختبارات صحة وقياس أداء موثق |
| تقييم الأخضر | تجميع مؤشرات مؤهلة ومعاينة أثر القواعد | سجل الطلبات والمراجعات والقضايا الفعلي | اعتماد الأرقام ومنهجية المؤشرات قبل أي منح تلقائي |
| توسيع محرك البحث عند الحاجة | تقييم محرك مشتق قابل للاستبدال | عقد الموفر نفسه | قياسات تثبت الحاجة، مقارنة تكلفة وأمن، اعتماد منفصل |

لا تستدعي هذه الخطة إدخال React أو shadcn أو محرك بحث خارجي إلى المشروع الثابت. لم تُضف حزمة أو خدمة مدفوعة. عند ظهور حاجة حقيقية إلى اعتماد جديد يجب تقديم النسخة المحددة والترخيص والصيانة والأمن والحجم والتكلفة والتوافق مع RTL وإمكانية الرجوع قبل دمجه.

## ٤. نموذج بيانات الشارات المقترح — غير منفّذ

يجب تثبيت أسماء الجداول النهائية بعد اعتماد أساس البيانات. الأسماء الآتية عقد منطقي، وليست جداول موجودة:

| الكيان المقترح | المعلومات الأساسية | القيد أو الغرض |
|---|---|---|
| `badge_definitions` | النوع، الأسماء العربية والإنجليزية، الوصف، اللون، الرمز، أولوية العرض | أربعة أنواع ثابتة؛ لا تتحول الألوان إلى سلم تفوق واحد |
| `badge_rule_versions` | نسخة القاعدة، طريقة الأهلية، المعايير، تاريخ السريان، الانتهاء، مصدر الاعتماد | النسخ المنشورة غير قابلة لإعادة الكتابة؛ كل منح مرتبط بنسخته |
| `badge_applications` | المتجر، النوع، مقدم الطلب، الحالة، تواريخ الإرسال والمراجعة | المالك يقدم لمتجره فقط، ولا يحدد قرار الموافقة |
| `badge_evidence` | مرجع تخزين خاص، نوع المستند، نتيجة الفحص، صاحب الوصول، الاحتفاظ | لا مستندات أو أرقام قانونية أو روابط عامة ضمن سجل العرض |
| `badge_evaluations` | فترة القياس، نسخة القاعدة، المؤشرات، حجم العينة، قرار وأسباب | مفتاح منع تكرار لكل متجر/قاعدة/فترة؛ السجل ليس منحاً بحد ذاته |
| `store_badge_grants` | المتجر، النوع، نسخة القاعدة، المصدر، المانح، السريان والانتهاء والإيقاف | منع أكثر من منح نشط للنوع نفسه على المتجر داخل معاملة واحدة |
| `badge_appeals` | المنح أو الطلب المعترض عليه، السبب، الموظف، القرار | مسار اعتراض لا يسمح لصاحب المتجر بمنح نفسه |
| `badge_audit_events` | الفاعل، الإجراء، الحالة السابقة واللاحقة، السبب، الوقت، مرجع النسخة | سجل أحداث غير قابل للتعديل أو الحذف من العميل |

**دورة الحالة المقترحة:** طلب جديد ← مقدّم ← تحت المراجعة ← موافق عليه ← فعّال؛ مع مسارات طلب أدلة إضافية، الرفض، الاعتراض، والانتهاء/التعليق/السحب. ينبغي فصل حالة الطلب عن حالة المنح؛ فقد يكون طلب التجديد قيد المراجعة ومنح سابق ما زال سارياً. انتهاء المدة يُحسب عند القراءة كذلك، فلا تعتمد سلامة العرض على نجاح مهمة مجدولة وحدها.

**الظهور العام:** نوع الشارة، عنوانها، تفسيرها العام، ونطاق العلامة أو المنطقة عندما يلزم. تاريخ التوثيق يظهر فقط إذا اعتمدت السياسة ذلك. تُعرض الشارات النشطة حالياً فقط؛ حتى لو تأخر تحديث فهرس البحث، لا يُعرض منح مسحوب أو منتهي. بطاقة المنتج تعرض شارتين كحد أقصى مع رابط لبقية الشارات. الرمادي محايد إذا كان جميع المتاجر مستوفين له.

### صلاحيات وأدلة التوثيق

- صلاحيات المنح والنشر والسحب مصدرها أدوار موثوقة بالخادم، لا حقول يرسلها العميل ولا `user_metadata` قابل للتعديل ذاتياً.
- مالك المتجر يرى طلباته وملاحظات المراجعة المسموح بمشاركتها. الدعم يدير الاعتراض وفق صلاحياته؛ لا يُمنح حق منح الأزرق أو الذهبي تلقائياً.
- كل قرار يدوي يتطلب سبباً وفاعلاً وتوقيتاً ومرجع أدلة؛ النشر وتحديث المنح والتدقيق يتمان معاً أو يفشلان معاً.
- الأدلة في تخزين خاص، وروابط تنزيل قصيرة الصلاحية بعد تحقق الخادم من دور الموظف وغرض الوصول. تمنع السياسات القراءة عبر URL مباشر أو API جانبي.
- تحتاج سياسة الملفات إلى أنواع وأحجام مسموحة، عزل الملفات قبل قبولها، فحص محتوى وامتداد، وخطة فحص برمجيات خبيثة. لا يُدّعى توافر المسح أو التشفير أو الاحتفاظ المنضبط قبل ربطها واختبارها.
- تُفصل بيانات الأدلة عن بيانات البحث العامة وتُحدد مدة حذفها واستثناءات الاحتفاظ والنسخ الاحتياطي بمراجعة قانونية وتشغيلية.

## ٥. عقود API للشارات المقترحة

تحافظ أسماء العمليات على قابلية تحويلها إلى RPC أو مسارات HTTP وفق الأساس المعتمد؛ لا حاجة لإنشاء مسارين متوازيين للمنطق نفسه.

| العملية المنطقية | الصلاحية | الضمان |
|---|---|---|
| قراءة شارات متجر | عام للمتجر المنشور | إسقاط عام آمن؛ نشاط وتاريخ سريان صحيحان |
| تقديم طلب/إضافة دليل | مالك المتجر | منع الانتحال؛ رفع خاص؛ تحقق ملف وحصة وحدود تكرار |
| قراءة طلبات واعتراضات المالك | المالك فقط | لا تسريب لطلبات أو مستندات متاجر أخرى |
| معاينة قاعدة جديدة | مشرف مخوّل | حساب أثر دون تعديل منح فعلي |
| نشر نسخة قاعدة | صلاحية إدارة القواعد | سبب وتاريخ سريان وتدقيق؛ لا تعديل تاريخي صامت |
| قرار منح/سحب/تعليق | مراجع مخوّل | تحقق حالة وصلاحية ومعاملة ذرية ومنع التكرار |
| تقييم الأخضر | مهمة خادم مخوّلة | قاعدة معتمدة ونافذة قياس ثابتة وأسباب قابلة للتفسير |

## ٦. البحث المنظم المقترح — المرحلة الأولى

المصدر المقترح PostgreSQL داخل مشروع Supabase المعتمد لاحقاً. تبدأ الفهارس من المتجر والمنتج والتصنيف والسعر والعملة والنشر، ثم البحث النصي و`pg_trgm` فقط إذا أثبتت عينات العربية والإنجليزية جدواه وتوافره. لا يُثبّت Meilisearch أو Typesense أو Algolia الآن.

### البيانات المطلوبة

- منتجات: معرفات مستقرة، اسم عربي وإنجليزي عند توفرهما، SKU علني فقط إن سمحت السياسة، العلامة، التصنيف/التصنيف الفرعي، السعر بوحدات العملة الصغرى، العملة، النشر والتوفر والعروض الصحيحة.
- متجر/بائع: الاسم والـslug والاسم العام المصرح بعرضه. لا اسم قانوني خاص أو بريد تسجيل أو بيانات طلبات داخل الفهرس.
- شارات: إسقاط للمنح السارية من سجل الخلفية، لا استخراج من الوصف ولا من الصور.
- تقييمات: متوسط وعدد مراجعات الشراء المؤهلة منفصلان عن تقييمات المجتمع. لا دمج صامت أو وصف غير الموثق بأنه شراء موثق.
- توصيل: مناطق منظمة، نطاق الدولة/المنطقة/المدينة، الاستثناءات، الرسوم والعملة، شروط الحد الأدنى، نسخة القاعدة والسريان.

### عقد الموفر

يحافظ `SearchProvider` على مدخلات البحث والاستعلام والوجهة والعملة والفلاتر والترتيب والترقيم. تُستبدل قراءة fixtures باستدعاء خلفي بعد الاعتماد، دون تغيير مكونات العرض أو كتابة قواعد أهلية مستقلة داخلها.

الاستجابة المقترحة: عناصر مطبّعة، نوع العنصر، إجمالي دقيق أو تقريب معلّم، أعداد facets، مؤشر الصفحة التالية، الفلاتر المطبقة، نسخة قواعد الشحن والشارات، وتفسير حالة الوجهة/الشحن. اقتراحات الإكمال مسار منفصل محدود النتائج وبفترة تأخير ٢٠٠–٣٠٠ مللي ثانية مع إلغاء الطلبات القديمة.

التحقق في الخادم يشمل طول الاستعلام والقيم المقبولة وحدود السعر والصفحات والعملة، قائمة ترتيب مغلقة، وعدد الشارات. لا SQL أو تعبيرات ترتيب حرة من العميل. قراءة عامة للمنشور فقط، وتحديد معدلات الطلبات دون تسجيل نصوص حساسة بلا سياسة.

### قواعد الفلاتر التي يجب أن تكون واحدة في الواجهة والخادم

1. تُجمع أنواع الفلاتر بـAND، وتُجمع الشارات المختارة داخل مجموعة الشارات بـOR كما يطلب الملخص 03، ما لم يعتمد تغيير واضح لاحقاً.
2. تُعرّف أعداد facets صراحة: عدد كل خيار بعد جميع الفلاتر الأخرى مع رفع فلتر المجموعة نفسها. يجب توثيق اختلاف ذلك عن العدد النهائي للنتائج.
3. الوجهة غير المكتملة تعطي توافقاً مبدئياً معلّماً، ولا تضمن أهلية أو توصيلاً مجانياً. عند عدم معرفة المدينة لا يُعتمد فلتر المجاني كحقيقة.
4. التوصيل المجاني مبني على القاعدة الفعلية للوجهة. إذا احتاج حد سلة، يعرض الشرط ولا يصف المنتج بأنه مجاني التوصيل دون استيفائه.
5. يجب حسم أولوية المناطق المتداخلة والاستثناءات قبل التنفيذ؛ لا يجوز اختيار «أول صف» من قواعد البائع عشوائياً.
6. المقارنة السعرية ضمن عملة متوافقة فقط. لا تحويل ضمني ولا ترتيب موحّد لعملات مختلفة دون سياسة صرف معتمدة.
7. ترتيب الصلة الافتراضي لا يعطي أولوية ذهبية أو ظهوراً مدفوعاً تلقائياً. جودة البائع والعروض تحتاج مؤشرات موثوقة ومعلّمة.
8. الترقيم محدود بحد أعلى، ويفضل المؤشر المركب بقيمة الترتيب ومعرف ثابت. عند تغير بيانات حيّة لا يُوعَد بثبات لقطة كاملة ما لم تُنفّذ لقطة بالفعل.
9. تعليق المتجر أو أرشفة المنتج يمنع القراءة من مصدر الحقيقة فوراً. فهرس مشتق أو ذاكرة مؤقتة لا يسمحان بإظهار محتوى مخفي أو دليل خاص.

### الإبطال والقياس

يشمل مفتاح الذاكرة المؤقتة الوجهة والعملة والفلاتر ونسخ القواعد. تعديل مناطق التوصيل أو العروض أو الشارات أو حالة المتجر ينشئ حدث إبطال قابل لإعادة المحاولة. التحديثات غير الحرجة تستهدف ≤٦٠ ثانية، والحظر والسحب يُتحقق منهما عند الاستجابة حتى مع تأخر الفهرس.

هدف p95 ≤٣٠٠ مللي ثانية **هدف قبول يحتاج قياساً**، وليس نتيجة حالية. يجب تعريف حجم الكتالوج وتوزيع النص العربي والإنجليزي والوجهات والفلاتر والتزامن وبيئة التشغيل قبل مقارنة PostgreSQL بمحرك آخر.

## ٨. إثبات القبول المطلوب بعد التنفيذ المعتمد

- محاولة منح ذاتي أو تغيير دور من المتصفح تفشل في قاعدة البيانات/API، بما فيها طلبات مباشرة خارج الواجهة.
- متجرا اختبار وحسابات مالك/بائع/مشتري/دعم تثبت العزل، ولا يقرأ موظف غير مخوّل دليلاً أو بيانات طلب.
- منع منح مكرر مع طلبين متزامنين، ومنع معالجة تقييم متكرر، وتوثيق التراجع والسحب والانتهاء والاعتراض.
- الأزرق/الذهبي لا يُمنحان من عدد المبيعات أو وصف منتج. الأخضر لا يُفعّل دون قواعد معتمدة وأسباب ونسخة ثابتة.
- سحب شارة وتعليق متجر يظهر أثرهما في القراءة المباشرة والبحث مع فهرس متأخر عمداً.
- تغيير الوجهة يغيّر أهلية الشحن والمجاني؛ حالات تداخل المناطق والاستثناءات وشرط الحد الأدنى ووجهة ناقصة مغطاة.
- بحث عربي وإنجليزي واسم متجر وslug واسم بائع عام، فلاتر متراكبة، OR للشارات، عملات غير متوافقة، صفحات وأعداد facets صحيحة.
- تجارب هوية وRTL/LTR ولوحة مفاتيح وقارئ شاشة وعرض ٣٦٠px وعودة/تحديث URL، مع حماية سرية الأدلة.
- اختبارات انحدار للسلة متعددة المتاجر وقبول الطلب والمخزون وخصوصية التسليم، واختبار استعادة نسخة احتياطية قبل وصف الإطلاق بأنه جاهز.

**حدود هذه المرحلة:** هذا المستند خطة منطقية مبنية على فحص الملفات والمواصفات. لا يثبت وجود تكامل OAuth أو سياسات RLS أو فهارس أو معاملات أو وظائف مجدولة أو صلاحيات إنتاجية. لم تُغيَّر المتطلبات المالية أو تدفقات الطلب، ولم تُضف أي خدمة أو SQL تنفيذي.
